# 云台固件 · 开发环境

> 从一行 `main.c` 到一颗跑在 168 MHz 上的芯片，中间有 **7 环**。
> 每一环的**谁干活、吃什么、吐什么、怎么验、断了什么样**，全在这一篇里。
>
> 本文是环境相关内容的**唯一文档**（原《开发环境搭建》已并入，见 §15–§18）：
> §0–§14 讲运行机制与排障，§15 讲语言选型，§16 讲实现决策与踩坑，§17 讲换机复现，§18 讲已知限制。
>
> 与其他文档的分工：`云台固件架构设计.md` 管代码怎么组织，`FOC技术栈.md` 管信号怎么走，
> `开发执行计划.md` 管哪天做什么，`硬件设计总结.md` + `IUO112_引脚配置清单.md` 管硬件事实。

## 1. 链路总表

| 环 | 谁干活 | 输入 | 输出 | 断在这里的症状 |
|---|---|---|---|---|
| 0 | 安装器 / 解压 | 下载的压缩包 | `%USERPROFILE%\tools\*` | 后面每一环都报"找不到命令" |
| 1 | `scripts\env.cmd` | 无 | 当前 cmd 的 PATH/INCLUDE/LIB | `cmake` 或 `arm-none-eabi-gcc` 不是内部命令 |
| 2 | `cmake.exe` | `CMakeLists.txt` + preset + toolchain 文件 | `build/arm/build.ninja` | `No CMAKE_C_COMPILER could be found` |
| 3 | `ninja` → `gcc` → `cc1` → `as` | `.c/.s` + 头文件 | `*.obj`（ELF 可重定位） | 编译错误 / `No such file or directory` |
| 4 | `ninja` → `gcc` → `collect2` → `ld` | `.obj` + `.a` + 链接脚本 | `gimbal.elf` | `undefined reference` / `region FLASH overflowed` |
| 5 | `objcopy` / `size` | `gimbal.elf` | `gimbal.bin` / `gimbal.hex` | 极少断；断了说明 ELF 本身有问题 |
| 6 | `openocd.exe` | `gimbal.elf` + USB | 芯片 Flash 里的字节 | `Error: open failed` / `no device found` |
| 7 | `cortex-debug` + `gdb` | `gimbal.elf` + `:3333` | 断点、变量、寄存器 | 卡在 `Launching` / `Remote connection closed` |

## 3. 第 1 环 · 环境注入

`scripts\env.cmd` 干三件事，全部只影响**当前 cmd 窗口**，不改系统环境变量。

```
① vswhere 定位 VS 安装目录
     └─→ call vcvars64.bat
            └─→ 一次性配好 PATH / INCLUDE / LIB / LIBPATH
                  （含 rc.exe、mt.exe 所在目录）

② 把 VS 自带的 CMake、Ninja 目录前插进 PATH

③ 把 %GIMBAL_TOOLS% 下的 arm-gnu-toolchain\bin、openocd\bin、ninja 前插进 PATH
```

**为什么 Windows 上必须有这一环**：Linux 上工具链装在 `/usr/bin` 就全局可用；
Windows 没有这个概念，`gcc`、`cl`、`cmake` 各在各的目录里，而且 MSVC 还额外依赖
`INCLUDE`（头文件搜索路径）和 `LIB`（库搜索路径）两个环境变量——**这两个变量没法用命令行参数替代**，
只能靠 `vcvars64.bat` 或手工设置。

**注意顺序**：`env.cmd` 里 VS 的 CMake/Ninja 是**前插**到 `%GIMBAL_TOOLS%\ninja` 之前的，
所以实际生效的是 VS 那一份。两份 Ninja 都能用，谁在前谁生效。

**验证**：

```bat
scripts\env.cmd
where cmake && where ninja && where cl && where arm-none-eabi-gcc && where openocd
```

`env.cmd` 末尾自带这五个 `where` 的检查，缺哪个会打印 `[缺少] xxx`。

## 4. 第 2 环 · 配置（`cmake --preset arm`）

这一环**不产出任何机器码**，只产出一份 `build.ninja`（给第 3 环看的施工图）。
它做的事比看起来多：

```
CMakePresets.json  ──preset=arm──┐
                                 ▼
              generator = Ninja，binaryDir = build/arm
              toolchainFile = cmake/toolchain-arm-none-eabi.cmake
                                 │
                                 ▼
       ┌──────────── 读 toolchain 文件 ────────────┐
       │ CMAKE_SYSTEM_NAME = Generic               │  ← 告诉 CMake "这是裸机交叉编译"
       │ CMAKE_TRY_COMPILE_TARGET_TYPE = STATIC_LIBRARY │ ← 探测编译器时不链接
       │ MCU_FLAGS = -mcpu=cortex-m4 -mthumb        │
       │             -mfpu=fpv4-sp-d16              │
       │             -mfloat-abi=hard               │
       └───────────────────┬───────────────────────┘
                           ▼
                  find_program(arm-none-eabi-gcc)
                           ▼
                  try_compile 探测 → 成功
                           ▼
        CMakeLists.txt 判断 CMAKE_CROSSCOMPILING = TRUE
                           ▼
              enable_language(ASM)  ← 只有固件需要 .s
                           ▼
              产出 build/arm/build.ninja + CMakeCache.txt
```

**两个容易看不懂的地方**：

1. **`CMAKE_TRY_COMPILE_TARGET_TYPE = STATIC_LIBRARY`**
   CMake 默认会用"编译一个空 main 并链接成可执行文件"来探测编译器。
   裸机环境下没有 `_start`、没有 libc 启动代码，链接必然失败，于是 CMake 会误判"编译器坏了"。
   改成 `STATIC_LIBRARY` 后只编译不链接，探测就通过了。

2. **四个 MCU flag 不只是给编译器看的，它决定了链接哪一套库**
   `-mfloat-abi=hard` + `-mfpu=fpv4-sp-d16` 组合出的 multilib 目录是
   **`thumb/v7e-m+fp/hard`**。GCC 会去这个子目录找 `libc_nano.a`、`libgcc.a`、`crt0.o`。
   如果把 `-mfloat-abi` 改成 `soft`，它会静默地去 `thumb/v7e-m/nofp` 找库——
   **编译一样通过，浮点运算全变成软件模拟**，8 kHz 环直接跑不动。
   这就是为什么这四个 flag 只写在 `cmake/toolchain-arm-none-eabi.cmake` 一处，
   `CMakeLists.txt` 里一个都不重复。

**验证这一环**：

```bat
cmake --preset arm
findstr /C:"-mfloat-abi=hard" build\arm\build.ninja
findstr /C:"FLAGS = " build\arm\build.ninja | findstr /C:"v7e-m"
```

## 5. 第 3 环 · 编译（`ninja` → `gcc` → `cc1` → `as`）

`ninja` 只是执行者，真正编译的是 GCC 内部的三层。用 `gcc -###` 抓到的真实调用：

```
arm-none-eabi-gcc.exe                    ← 驱动（driver），只做参数翻译和调度
   │  -mcpu=cortex-m4 -mthumb -mfpu=fpv4-sp-d16 -mfloat-abi=hard
   │  -DSTM32F405xx -DUSE_HAL_DRIVER -I… -O0 -g3 -std=gnu11 -Wall …
   ├─→ cc1.exe                            ← 真正的编译器
   │      main.c  →  C:\…\Temp\ccv4IRZh.s   （预处理 + 编译，产出汇编）
   └─→ as.exe                             ← 汇编器
          ccv4IRZh.s  →  main.c.obj         （汇编 → ELF 可重定位目标）
```

**24 个编译单元**：

| 来源 | 数量 | 说明 |
|---|---|---|
| `stm32/` 官方 | 21 | `system_stm32f4xx.c` + 20 个 HAL 模块 → 归档成 `libstm32_hal.a` |
| `src/` 自有 | 3 | `main.c`、`uart.c`、`startup_stm32f405xx.s` |

`startup_stm32f405xx.s` 走的是 `as`，但它没有经过 `cc1`——汇编文件直接进汇编器。

**为什么 `ninja` 而不是手写 Makefile**：
改了 `board.h` 之后要重编哪几个 `.obj`，靠人算一定会漏；`ninja` 从 `build.ninja` 里的
头文件依赖表算，改一个头自动重编所有包含它的文件。24 个单元时还看得过来，
到 W10 有 40+ 个单元、十几层 include 时，手工维护就是灾难。

**验证这一环**：

```bat
cmake --build --preset arm
:: 期望每个文件一行 [N/M] Building C object ...
:: 结尾出现 Memory region / FLASH / RAM 表
```

想单独看某个文件的真实调用链（排查"为什么这个宏没生效"最有效）：

```bat
arm-none-eabi-gcc <所有flag> -### -c src\app\main.c -o NUL
```

## 6. 第 4 环 · 链接（`gcc` → `collect2` → `ld.exe`）

`gcc` 自己**不链接**，它把活交给 `collect2`，`collect2` 再去调真正的 `ld.exe`。
这一层中转不是多余的：`collect2` 负责收集构造函数（`.init_array`）、
拼出 `crt0.o`/`crti.o`/`crtbegin.o` 这些启动文件、并按 multilib 选对库路径。

真实的链接参数（从 `build/arm/build.ninja` 提取）：

```bat
arm-none-eabi-gcc
    -mcpu=cortex-m4 -mthumb -mfpu=fpv4-sp-d16 -mfloat-abi=hard
    -T ld/STM32F405RGTx_FLASH.ld      ← 内存布局由这个文件说了算
    --specs=nano.specs                 ← 用 newlib-nano（省 ~50KB）
    --specs=nosys.specs                ← 系统调用打桩（裸机没有 OS）
    -u _printf_float                   ← 强制链入浮点格式化
    -Wl,--gc-sections                  ← 丢弃没被引用的段
    -Wl,--no-warn-rwx-segments
    -Wl,--print-memory-usage           ← 打印 RAM/FLASH 占用
    -Wl,-Map=build/arm/gimbal.map
    -o build/arm/gimbal.elf
    main.c.obj uart.c.obj startup_stm32f405xx.s.obj libstm32_hal.a
```

`collect2` 实际拼出来的库和启动文件（`-###` 抓到）：

```
…/thumb/v7e-m+fp/hard/crti.o        ← multilib 路径，由四个 MCU flag 决定
…/thumb/v7e-m+fp/hard/crtbegin.o
…/thumb/v7e-m+fp/hard/crt0.o
-L …/thumb/v7e-m+fp/hard
-lc_nano  -lnosys  -lgcc
```

**四个链接选项，每一个都对应一个踩过的坑**：

| 选项 | 不加会怎样 |
|---|---|
| `--specs=nano.specs` | 链 full newlib，Flash 直接多占 50 KB |
| `--specs=nosys.specs` | 报 `undefined reference to _write/_sbrk/_close…` 几十条 |
| `-u _printf_float` | **`printf("%f")` 不报错，直接输出乱码**。nano 版为了省空间把浮点格式化整个删了，符号不存在就不链，于是 `%f` 走空实现 |
| `-Wl,--gc-sections` | `libstm32_hal.a` 里 21 个 `.obj` 全部链进去，哪怕只用了 3 个 HAL 模块 |

**链接后的真实内存布局**（`size -A` + `readelf -l` 实测）：

| 段 | 大小 | VMA | 说明 |
|---|---|---|---|
| `.isr_vector` | 392 B | `0x0800_0000` | 中断向量表，98 项 × 4 B = 16 系统异常 + 82 个 IRQ，**必须**在 Flash 最开头 |
| `.text` | 21,160 B | `0x0800_0190` | 代码 |
| `.rodata` | 1,108 B | — | 常量、字符串 |
| `.ARM.exidx` | 8 B | — | 异常展开索引 |
| `.init_array` / `.fini_array` | 4 B / 4 B | — | C 运行时构造/析构表 |
| `.data` | 468 B | `0x2000_0000`（VMA）<br>`0x0800_589C`（LMA） | 有初值的全局变量：**存 Flash，启动时拷到 RAM** |
| `.bss` | 1,464 B | `0x2000_01D4` | 零初始化全局变量，**不占 Flash** |
| `._user_heap_stack` | 4,100 B | `0x2000_078C` | 栈 4 KB + 堆 0 + 对齐，一直预留到 `_estack = 0x2002_0000` |

**`.data` 是谁从 Flash 搬到 RAM 的**——这一环最容易被忽略，但漏了就是静默故障：

不是 `crt0.o`，是**我们的启动文件** `startup_stm32f405xx.s` 里的 `Reset_Handler`。
它用 5 个**链接脚本导出的符号**做搬运和清零：

```asm
ldr r0, =_sdata      ; 0x20000000  RAM 里的目标起点
ldr r1, =_edata      ; 0x200001D4  目标终点
ldr r2, =_sidata     ; 0x0800589C  Flash 里的初值来源
CopyDataInit:  ldr r4,[r2,r3] / str r4,[r0,r3] / adds r3,#4
ldr r2, =_sbss       ; 0x200001D4
ldr r4, =_ebss       ; 0x2000078C
FillZerobss:   str r3,[r2] / adds r2,#4
bl __libc_init_array ; 跑 .init_array 里的构造函数
bl main
```

实测符号值（`nm`）：

```
20000000 D _sdata     ← .data 在 RAM 的起点
200001d4 D _edata     ← 起点 + 468 B
0800589c A _sidata    ← 与程序头里 .data 段的 PhysAddr 完全一致
200001d4 B _sbss      ← 紧跟 .data
2000078c B _ebss      ← .bss 结束
20020000 R _estack    ← RAM 末尾
```

**这 5 个符号名是启动文件和链接脚本之间的口头约定**，编译器不检查。
链接脚本里改一个名字（比如 `_sidata` 写成 `_sidata_`），链接**照样通过**，
只是那行 `ldr` 会解析成一个未定义符号 → 链接报错（好情况），
或者被另一个同名符号顶替 → 搬错地址（坏情况，上板后全局变量全是垃圾）。

顺带一个反直觉的实测结果：`crt0.o` **被链接进来了，但它的 `_start` 被 `--gc-sections` 丢掉了**。
`nm` 里能查到 `__libc_init_array`（`0x08003704`），查不到 `_start`——
因为入口点被链接脚本指定为 `Reset_Handler`（`Entry point 0x8000be9`），
`_start` 没有任何地方引用，于是被回收。**这是正常且期望的**：
`.data` 搬运和 `.bss` 清零都由启动文件自己做了，不需要 libc 的 `_start` 再来一遍。

程序头（`readelf -l`）解释了第 5 环为什么是这个数字：

```
LOAD  VirtAddr 0x08000000  PhysAddr 0x08000000  FileSiz 0x0589C  Flg RWE   ← Flash 常驻
LOAD  VirtAddr 0x20000000  PhysAddr 0x0800589C  FileSiz 0x001D4  Flg RW    ← .data 初值
LOAD  VirtAddr 0x2000078C  PhysAddr 0x08005A70  FileSiz 0x00000  Flg RW    ← .bss，无文件内容
```

**验证这一环**：

```bat
:: 向量表首字必须是栈顶地址 0x20020000
arm-none-eabi-objdump -s -j .isr_vector build\arm\gimbal.elf | more
:: 次字必须是 Reset_Handler 地址 + 1（Thumb 位）
arm-none-eabi-nm build\arm\gimbal.elf | findstr "Reset_Handler _estack"
:: 确认浮点格式化真的链进来了
arm-none-eabi-nm build\arm\gimbal.elf | findstr "_printf_float"
```

## 7. 第 5 环 · 格式转换（`objcopy` + `size`）

链接产物 `gimbal.elf` 是**给调试器看的**，里面有段表、符号表、`.debug_*` 调试信息，
体积 126,560 B。烧进 Flash 的只能是纯字节，所以要做两次 `objcopy`：

```bat
arm-none-eabi-objcopy -O binary gimbal.elf gimbal.bin   :: 裸二进制，23,152 B
arm-none-eabi-objcopy -O ihex   gimbal.elf gimbal.hex   :: Intel HEX，带地址记录
arm-none-eabi-size              gimbal.elf              :: text/data/bss 三行摘要
```

**23,152 这个数是怎么来的**（不是猜的，是上面程序头加出来的）：

```
Flash 常驻段 FileSiz   0x0589C = 22,684 B
.data 初值段 FileSiz   0x001D4 =    468 B
                        ─────────────────
                        合计     23,152 B   ← 与 gimbal.bin 大小完全一致
```

`.bss`（1,464 B）和 `._user_heap_stack`（4,100 B）**不出现**在 `.bin` 里——
它们是 NOBITS 段，运行时由启动代码清零/预留，Flash 里不需要存任何字节。
**这是"Flash 占用"和"RAM 占用"为什么不是一回事的最直观证据**：

| 指标 | 数值 | 占芯片容量 |
|---|---|---|
| FLASH | 23,152 B | 896 KB 的 **2.52%** |
| RAM | 6,032 B | 128 KB 的 **4.60%** |
| CCMRAM | 0 B | 64 KB 的 **0.00%** |

`--print-memory-usage` 打印的就是这张表，每次构建自动出现，不用手动查。

**`-O binary` 和 `-O ihex` 的区别**：前者是纯字节流，烧录器从 `0x08000000` 开始连写；
后者每行带地址，可以跳着烧（比如只烧参数区）。本项目用 `.bin` 就够，
`.hex` 是给"参数区单独更新"这种场景留的。

## 8. 第 6 环 · 烧录（`openocd` → ST-Link → SWD → Flash）

```bat
openocd -f interface/stlink.cfg -c "transport select swd" -f target/stm32f4x.cfg ^
        -c "program build/arm/gimbal.elf verify reset exit"
```

这一环内部有四段，每一段都可能独立断：

```
openocd.exe
  │
  ├─① 加载 interface/stlink.cfg
  │     adapter driver st-link
  │     st-link vid_pid 0x0483 0x3744 … 0x3757    ← ST-Link 的 USB 识别码清单
  │     ↓  这一段失败 = USB 层问题（没插、驱动没装、被别的软件占用）
  │
  ├─② 加载 target/stm32f4x.cfg
  │     声明 F405 的 Flash 控制器、SRAM 地址、复位方式
  │     ↓  这一段失败 = 配置找不到（-s 脚本路径问题）
  │
  ├─③ transport select swd → 建立 SWD 链路
  │     需要 4 根线：SWCLK、SWDIO、GND、3.3V（目标电压检测）
  │     ↓  这一段失败 = 接线问题（飞线没焊好、目标没上电）
  │
  └─④ program / verify / reset
        把 ELF 里的 LOAD 段写进 Flash，读回校验，复位运行
        ↓  这一段失败 = Flash 保护、写保护选项字节、供电不足
```

**三个端口**（`openocd` 启动时自动监听，实测输出）：

| 端口 | 用途 |
|---|---|
| `3333` | **GDB 远程调试**（第 7 环用这个） |
| `4444` | telnet 命令行（手工读寄存器、复位、`mdw` 看内存） |
| `6666` | TCL 脚本接口 |

**当前状态**：OpenOCD 已装、两段配置都能正确加载、4444/6666 正常监听，
但走到 ③ 就报 `Error: open failed`——因为 ST-Link 没插或目标板没上电。
这是**预期结果**，不是配置错误。

**板上没有调试座**，只有测试点：`TP1 = NRST`、`TP2/TP3 = SWCLK`、`TP4 = SWDIO`。
必须飞线或做探针治具，另接 GND 与 3.3 V。

**验证这一环**（分两步，先验链路再验烧录）：

```bat
:: 第一步：只建链，不烧
openocd -f interface/stlink.cfg -c "transport select swd" -f target/stm32f4x.cfg
:: 成功标志：出现 "Info : stm32f4x.cpu: hardware has 6 breakpoints" 且不退出

:: 第二步：烧 + 校验 + 复位
openocd -f interface/stlink.cfg -c "transport select swd" -f target/stm32f4x.cfg ^
        -c "program build/arm/gimbal.elf verify reset exit"
:: 成功标志：最后一行 "** Verified OK **"
```

## 9. 第 7 环 · 调试（VSCode → gdb → openocd → 芯片）

`.vscode/launch.json` 里每个字段都对应链上的一个环：

| 字段 | 值 | 对应哪一环 |
|---|---|---|
| `servertype` | `openocd` | 第 6 环 |

```
VSCode cortex-debug
   └─→ 启动 openocd（后台进程，占用 3333）

          └─→ target remote :3333
                 └─→ openocd → ST-Link → SWD → 芯片
```

## 14. 一句话总结

这条链上有 **6 个静默失败点**——它们不报错，只是行为不对，而且症状都伪装成"算法有问题"：

| 静默失败 | 伪装成 |
|---|---|
| `-mfloat-abi` 写成 soft | 控制环跑不动、抖动，看起来像 PID 参数没调好 |
| 漏 `-u _printf_float` | `printf("%f")` 输出乱码，看起来像角度算错了 |
| 漏 `--specs=nosys.specs` | 链接报一堆 `undefined reference`，看起来像库坏了 |
| 链接脚本 `_estack` 写错 | 程序跑飞/进 HardFault，看起来像栈溢出 |
| 向量表不在 `0x0800_0000` | 烧进去不跑，看起来像芯片坏了 |
| `_sidata/_sdata/_edata` 名字对不上 | 有初值的全局变量是随机值，看起来像"上电参数丢了" |

**所以这张表比任何一节都值得先记住。** 编译器不会替你检查这六件事。

## 15. 为什么是 C11 + 裸机

这不是习惯，是四条硬件约束推出来的：

| 硬件事实 | 推论 |
|---|---|
| 8 kHz 控制环 = 125 µs/周期 | 必须硬实时、无 GC、无运行时抖动 → 排除 MicroPython（单次浮点运算 10~50 µs，差一个数量级） |
| TIM1 主 / TIM3·TIM4 从 + RCR=2 触发 ADC + DMA 扫描 | 这类组合 HAL 表达不出来，必须落寄存器 → 语言越"高层"越要绕回裸寄存器 |
| 官方 HAL / CMSIS / 全部寄存器头文件是 C | 换语言要处理 ABI 与 `extern "C"` 边界，收益为零 |
| FPU 是 FPv4-SP，只有单精度 | `double` 走软件浮点，慢 10~50 倍；`0.5` 字面量默认是 double，是本项目最高频的隐性坑 |

- **C++ 可行**（SimpleFOC 就是 C++），但本项目 22 个模块无多态需求，收益≈0、复杂度+。
- **Rust 可行**，但 F405 的主从定时器同步与触发链多数仍要退回 PAC 裸寄存器，单人 13 周成本 > 收益。
- **MicroPython 不可行**，实时性差两个数量级。

这条结论直接落到两个构建选项上：`-mfloat-abi=hard`（第 2 环）和 `-Wdouble-promotion`（§16.4）。

## 16. 关键实现决策（踩坑记录）

这一节的每一条都是"当时不这么做就编不过 / 跑不对"。

### 16.1 `hal_conf.h` 用 3 行 shim 转发

架构文档 §5 规定配置叫 `hal_conf.h` 并放在 `src/common/`，但 HAL 源码里硬编码
`#include "stm32f4xx_hal_conf.h"`，而 `stm32/` 里的官方代码不允许改。

解法：`src/common/hal_conf.h` 放真正的配置，另加 `src/common/stm32f4xx_hal_conf.h`
只写一行 `#include "hal_conf.h"`。这是唯一同时满足"命名约定"和"官方代码不动"的写法。

### 16.2 printf 走 UART5，不是 USART2

板上两个串口分工不同：**J4 = UART5（PC12/PD2）= 调试口**，J3 = USART2（PA2/PA3）= 主机协议口。
`printf` 重定向到 UART5。若混用，W10 调协议时调试输出会污染协议数据。

### 16.3 `_sbrk` 给 1 KB 静态堆

`--specs=nosys.specs` 提供的 `_sbrk` 直接返回失败，newlib 的 `printf` 在某些格式化路径上会申请内存，
失败后行为不可预期。`uart.c` 里给了 1 KB 静态区兜底。
**应用层仍然禁止 `malloc/free`（架构文档 §14.6）**，这里只是防止库函数失败。

### 16.4 告警策略：`-Wdouble-promotion` 是故意开的

只对本工程代码开 `-Wall -Wextra -Wshadow -Wdouble-promotion`，`stm32/` 不加 `-Werror`
（HAL 在 GCC 13+ 有已知告警，加了会卡住整个构建）。

`-Wdouble-promotion` 会揪出 `x * 0.5` 这类把 float 提升成 double 的写法——在 FPv4-SP 上这不是风格问题，
是性能问题。代价是 `printf("%f", f)` 会告警，必须写 `(double)f`；
这是可接受的，因为项目里打印浮点的次数远少于做运算的次数。

### 16.5 链接脚本预留参数区

FLASH 按 **896 KB** 编址，末 128 KB 扇区（sector 11，`0x080E0000`）不参与代码链接，
留给参数双备份（两份各 64 KB）。这样代码永远长不进参数区，不需要靠人工盯着 `.map` 文件。

### 16.6 `hal_conf.h` 里模块的 include 顺序不能随意排

`stm32f4xx_hal_adc.h` 直接使用 `DMA_HandleTypeDef` 却没有自己 include `dma.h`，
所以 `hal_conf.h` 必须按 ST 模板的顺序：**RCC → GPIO → EXTI → DMA → CORTEX → FLASH → PWR → ADC → SPI → TIM → UART → USART**。

按字母序排会在 `DMA_HandleTypeDef` 处报 `unknown type name`，并连带 20 多个文件一起失败。

### 16.7 MSVC 编译中文注释要加 `/utf-8`

源码是 UTF-8，MSVC 默认按系统代码页（936/GBK）解析，中文注释会触发 C4819 并可能吃掉字符。
`src/tests/CMakeLists.txt` 里对 MSVC 单独加了 `/W4 /utf-8`，对 GCC/Clang 用 `-Wall -Wextra -Wdouble-promotion`，
两边都不影响对方。

### 16.8 官方头文件"宁多勿少"

第一次编译连踩三次"少拷了一个头文件"：

| 报错 | 原因 |
|---|---|
| `m-profile/cmsis_gcc_m.h: No such file` | CMSIS 6 把核心头拆进了子目录，平铺拷贝会漏 |
| `Legacy/stm32_hal_legacy.h: No such file` | `stm32f4xx_hal_def.h` 无条件 include 它 |
| `stm32f4xx_ll_adc.h: No such file` | `stm32f4xx_hal_adc.h` 依赖 LL 层头文件 |

头文件多拷几 MB 没有代价（不参与编译就不占 Flash），少拷一个就要多跑一轮构建。
所以现在 `stm32/hal/inc/` 是**全量 100 个头 + Legacy/**，只裁器件系列（F4 全系列 27 MB → 3 个头）。

## 18. 已知限制

1. **只能 SWD 烧录**。BOOT0 固定接地、板上无 USB，量产需要治具或测试点阵列。
2. **`stm32/` 与工具链都不入 git**：`stm32/` 已入库（11 MB，可接受）；工具链在 `%USERPROFILE%\tools`，`build/` 已在 `.gitignore`。
3. **host 测试绑定 MSVC**。CMake/Ninja/编译器三者都来自 Visual Studio，换机器必须装 VS（含 C++ 工作负载）。
   若将来要上 CI 或换 Linux，建议改装 MinGW-w64，`CMakeLists.txt` 不用改（已按编译器 ID 分支）。
4. **没有 SVD 文件**。Cortex-Debug 暂时不能按外设名看寄存器，需要时从 ST 官网补 `STM32F405.svd` 并填进 `launch.json` 的 `svdFile`。
5. **烧录链路未实测**。OpenOCD 已装、配置能加载、端口能监听，但没有板子和探针接上，真正的 `program/verify` 没跑过。
6. **代码尚未上板**。编译通过只证明"语法、链接、内存布局"正确，不证明"时钟真的跑在 168 MHz、串口真的出字"。
7. **构建期 6 条 nosys 告警是预期的**。`_close/_fstat/_isatty/_kill/_lseek/_read is not implemented` 来自
   `--specs=nosys.specs` 的空实现；printf 只用到 `_write`，其余系统调用在本项目中无意义。
