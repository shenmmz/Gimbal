>
> 1. **不依赖不存在的硬件能力** —— 没有电流采样就不设计电流环；母线测不准就不用母线前馈。

> 3. **把硬件限制写进文档** —— 附录 B 每一条都标注了"固件怎么绕"，避免后来者当成软件 bug 反复排查。

**怎么读这份文档**

## 1. 本文解决什么问题

定义固件的**分层边界、模块职责、文件划分、命名规则、运行时序**。

读完后应当能回答四个问题：

1. 某个功能该写在哪个文件里？
2. 它由哪个中断驱动、以什么频率运行？
3. 它能调用谁、不能被谁调用？
4. 它对外暴露哪些接口？

本文**不包含**具体实现代码。实现阶段以本文的接口签名为准，接口变更必须先改本文。

## 2. 开工前必须确认的 5 件事

这 5 项**阻塞编码**。不确定的话，对应模块写了也要推翻重写。

| # | 待定内容 | 阻塞哪个模块 | 不定的后果 |
|---|---|---|---|
| 1 | **霍尔安装角度 90° 还是 120°** → **按 120° 设计，待 W1 实测确认** | `algorithm/hall.c` | 解算公式按 120° 版写（§7.2.1）。实测若为 0° 则 atan2 方案不成立；"120°"是机械角还是电角度也要一并分清楚，见第 3 项 |
| 2 | **M1 / M2 / M3 对应哪个轴**（yaw / pitch / roll） | `control/gimbal.c` | 轴映射表错，自稳方向反了会直接失控 |
| 3 | **极对数 + 霍尔读的是哪个磁场**（转子多极磁钢 / 独立 2 极角度磁环） | `algorithm/hall.c` | 前者：机械角有 p 个解、必须 p 不是 3 的倍数；后者：单圈绝对。**两种情况的架构完全不同** |
| 4 | **上位机协议**：自定义 or MAVLink | `app/protocol.c` | 决定帧格式、命令表、地面站兼容性 |
| 5 | **PWM1–4 是输入还是输出**（PA6 复用问题） | `app/mode.c` | 决定 `MODE_RC` 模式是否可行 |

**确认优先级**：2、3 必须最先定（M2 阶段就要用）；4、5 可以在 M7 之前定。

第 3 项有一个 5 分钟就能做完的验证，不需要写代码、不需要示波器——见 §7.2.1 末尾。**这是整个项目里性价比最高的一次测量。**


> **原待定项"母线分压电阻是否修正"已关闭** —— 硬件冻结，不改板。该路只能做欠压检测，前馈用固定常量，详见附录 B 的 B3。

## 3. 硬件事实 → 架构约束

架构不是凭空设计的。下面 6 条硬件事实直接决定了分层方式和控制链形状，**改架构前先看这张表**。

| # | 硬件事实 | 对架构的影响 |
|---|---|---|
| 1 | **无相电流采样**（LSS 直接接地） | 控制链只有 3 层：位置→速度→电压；必须靠反电动势前馈补动态 |
| 2 | **霍尔给绝对角度**（每轴 2 颗线性霍尔，120° 摆放） | 上电即知角度，**不需要预定位、不需要开环强拖**；状态机大幅简化。**前提是霍尔读的是单圈 2 极角度磁环**——若读的是多极转子磁钢，绝对角有 p 个解，这条要打折，见 §7.2.1 |
| 3 | **3 路 nFAULT 悬空** | 无法感知过流/过温，只能靠"指令饱和 + 角度不跟随"做软件堵转判断 |
| 4 | **EN 全部上拉固定** | 无法单相关断，只能整片 nSLEEP（唤醒 1.5 ms） |
| 5 | **IMU 无中断引脚**（PC6 被加热占用） | IMU 只能轮询，**控制时基必须由定时器决定**，不能由数据就绪驱动 |
| 6 | **无 NTC、无电流检测** | 温度只能用 MCU 内部传感器看趋势，不能做精确温补 |

**这 6 条里最关键的是第 2 条。** 常规无感 FOC 要花大量代码做预定位、强拖、观测器收敛；本方案因为霍尔直接给出角度，这些全部不需要。整个 `control/` 层因此可以写得非常薄。

但第 2 条是**有条件的**，不是无条件的。"绝对角度"成立需要霍尔读的是单圈 2 极磁环（一圈机械对应一个电周期）。如果霍尔对着的是转子多极磁钢，它给的是电角度，机械角有 p 个解——上电时不知道在哪一解上。这个前提必须先验证，验证方法在 §7.2.1 末尾，5 分钟。

### 3.1 为什么 FOC 必须自己写

这个问题被反复提起，所以在架构里定死：**电机侧的换相与控制逻辑，全部由本固件实现，没有任何现成驱动可用。**

**SS6343M 不是电机驱动器，是功率级。** 规格书写的是"为每个半桥提供使能和 PWM 输入"——它的全部职责是把 3 路 PWM 变成三相桥臂的开关动作（内部互补 + 40 ns 死区），外加电荷泵和过流检测。**没有霍尔输入、没有换相表、没有角度接口、没有 FOC。** 一颗 SS6343M 就是一个完整三相全桥，对应 3 路 PWM 输入。

板级反证更直接：

| 板上有什么 | 数量 | 如果电机自带驱动，这些是什么 |
|---|---|---|
| SS6343M | 3 颗（每轴 1 颗三相桥） | 完全多余 |
| 霍尔 | 6 路（每轴 2 颗） | 完全多余 |
| MCU → 驱动 PWM | 9 路（每轴 3 相） | 完全多余 |

三个都多余，说明它们就是为"MCU 直接驱动裸电机"准备的。结论没有余地：**要自己写。**

**但要写的东西比教科书 FOC 少一半。** 硬件砍掉了三块最麻烦的：

| 环节 | 标准 FOC 要做什么 | 本方案 | 为什么能省 |
|---|---|---|---|
| 电流环 | Clarke/Park 变换 + 2 个电流 PI + 反 Park + 抗饱和 | **完全不做** | 无采样电阻，LSS 直接接地（附录 B1） |
| 死区 | 互补 PWM 配置 + 死区补偿 + 窄脉冲处理 | **不做** | SS6343M 内部 40 ns 死区，MCU 只给单路占空比 |
| 启动 | 预定位 + 开环强拖 + 观测器收敛 | **不做** | 霍尔给绝对角（情况 A 前提下） |
| 观测器 | 磁链/反电动势观测器 + 锁相环 | **不做** | 有传感器 |

剩下真正要写的只有四件事：

| 要写什么 | 在哪个文件 | 干什么 | 里程碑 |
|---|---|---|---|
| 角度解算 | `algorithm/hall.c` | 2 路线性霍尔 → 120° 重构 → atan2 → 角度 | M2 |
| 电压矢量 → 占空比 | `algorithm/svpwm.c` | uα/uβ → 3 路占空比 | M3 |
| 串级控制 | `control/axis.c` | 位置 P → 速度 PI → 电压幅值 | M4 |
| 前馈 | `control/feedforward.c` | 反电动势、重力补偿 | M6 |

所以准确的说法是：**这是"电压模式 FOC"——保留了 FOC 的骨架（磁场定向 + SVPWM），缺了电流环这个心脏。** 严格讲它不满足教科书 FOC 的定义（没有 i_d/i_q 闭环），但对云台这种负载恒定、转速低的场合够用，而且是被硬件逼出来的唯一选择。

**开源库能不能直接用？** 最近的参考是 SimpleFOC，但它假设角度传感器是它的 `Sensor` 子类（编码器或 3 个数字霍尔），本方案是 2 颗线性模拟霍尔 + 120° 重构，传感器层得自己写；它的 PWM 驱动假设 3 路独立半桥，这点倒是和 SS6343M 吻合。结论：**可以当参考读，尤其 SVPWM 和 PID 那两段，但不要指望移植。** 它的 C++ 类风格、动态分配也和本文档的裸机 C 约定冲突。

**工作量归属：M2 1.8 周 + M3 1.2 周 + M4 2.2 周 = 5.2 周，占 13 周演示版的 40%。** 这不是"顺手写一下"的部分，是整个项目的技术主体。

## 4. 分层

### 4.1 五层

| 层 | 目录 | 职责 | 运行频率 |
|---|---|---|---|
| 应用层 | `app/` | 模式管理、协议解析、保护、状态机、参数 | 100 Hz |
| 控制层 | `control/` | 位置环 → 速度环 → 电压指令 | 8 kHz |
| 算法层 | `algorithm/` | SVPWM、霍尔解算、姿态、滤波、标定 | 8 kHz |
| 驱动层 | `driver/` | PWM、ADC、SPI、UART、GPIO、NVM | 中断驱动 |
| 硬件 | — | 3× SS6343M、6× 霍尔、ICM-42688-P | — |

### 4.2 分层规则（强制）

1. 上层可以调下层，**下层不得反向调用上层**。
2. 层间只通过 `.h` 里声明的接口通信，**不共享全局变量**。
3. `algorithm/` 和 `control/` 是**纯计算**，不含任何寄存器操作，可脱离硬件在 PC 上单元测试。
4. 所有引脚和硬件常量只允许在 `common/board.h` 里定义一次，其他文件**禁止硬编码引脚号**。
5. `driver/` 里不允许出现业务判断（详见 §7.1）。

### 4.3 调用关系

实线为直接调用，方向永远向下。

```
                        ┌──────────────────────────────┐
                        │  app/  main.c                │
                        │  fsm · mode · protect        │
                        │  protocol · params · thermal │
                        └───────┬──────────────┬───────┘
                                │              │
                 ┌──────────────▼──┐      ┌────▼─────────────┐
                 │ control/        │      │ algorithm/       │
                 │ gimbal          │      │ calibration      │
                 │  └─ axis        │      │ imu              │
                 │      ├─ pid      │      │ filter           │
                 │      └─ feedfrwd │      └────┬─────────────┘
                 └──────┬───────────┘           │
                        │                       │
                 ┌──────▼───────────────────────▼──────┐
                 │ algorithm/  hall · svpwm             │
                 └──────┬───────────────────────────────┘
                        │
                 ┌──────▼───────────────────────────────┐
                 │ driver/  pwm · adc · spi · uart      │
                 │          gpio · nvm · timebase       │
                 └──────┬───────────────────────────────┘
                        │
                 ┌──────▼───────────────────────────────┐
                 │ stm32/         HAL · CMSIS           │
                 └──────────────────────────────────────┘
```

**8 kHz 中断里的实际调用链**（最热的一条路径，必须背下来）：

```
ADC 转换完成
  └─ adc_get_raw()           driver
     └─ hall_decode()        algorithm    两路 ADC → 机械角 / 电角度
        └─ gimbal_step()     control      三轴协调、轴映射
           └─ axis_step()    control      位置环 → 速度环 → 电压指令
              ├─ pid_step()      control
              └─ feedforward()   control
           └─ svpwm_calc()   algorithm    α-β → duty[3]
              └─ pwm_set_duty()  driver    写 CCR
```

这条链总预算 **40 µs**（8 kHz × 40 µs = 32% CPU）。

### 4.4 不用 RTOS，裸机 + 中断 + 主循环

**结论：本项目不引入 RTOS。** 但这不是"RTOS 不好"，而是这个项目的并发需求根本不成立。

#### CPU 预算：空闲 55%

| 项 | 占用 | 算法 |
|---|---|---|
| 控制中断 | 32% | 8 kHz × 40 µs |
| IMU 中断 | 5% | 1 kHz × 50 µs |
| 应用层 | 5% | 100 Hz × 500 µs |
| 串口 / 其他 | 3% | 事件驱动 |
| **空闲** | **55%** | — |

**没有并发压力，RTOS 要解决的问题在这里不存在。**

#### 三个硬理由

| # | 理由 | 说明 |
|---|---|---|
| 1 | **8 kHz 控制环进不了任务** | 控制周期 125 µs，比 FreeRTOS 默认 tick（1 ms）还短 8 倍。任务切换开销 1~3 µs，调度抖动可达几十 µs，直接吃掉 40 µs 预算的一大块。控制环**只能**留在中断里，用最高优先级保证确定性 |
| 2 | **临界区会关中断** | RTOS 内核进出临界区要屏蔽中断。哪怕只屏蔽几微秒，也会让 8 kHz 中断的抖动变成不可预测。而云台的指向精度完全依赖这个抖动有多小 |
| 3 | **代价全是净支出** | 多 8~16 KB RAM（任务栈）、多 15 KB Flash、多三类调试问题（栈溢出、优先级反转、死锁）。换来的只有"不用手写时间片判断" |

一句话：**RTOS 换来的好处（自动调度、阻塞式 API）这个项目用不上，付出的代价（调度抖动、关中断）这个项目承受不起。**

#### 三层结构

| 层 | 触发 | 内容 | 写法 |
|---|---|---|---|
| 中断层 | 硬件 | 8 kHz 控制、1 kHz IMU | 只做数据搬运 + 调用 `xxx_step()` |
| 主循环层 | `while(1)` | 100 Hz 应用、协议解析、10 Hz 热控 | 非阻塞状态机 |
| 空闲 | `__WFI()` | 等中断 | 省电、降噪 |

`main.c` 的主循环长这样：

```c
while (1) {
    if (s_app_tick) { s_app_tick = 0; app_step(); }   // 100 Hz
    protocol_poll();                                  // 非阻塞收包
    thermal_poll();                                   // 10 Hz 慢环
    __WFI();                                          // 无事就睡
}
```

#### 唯一真正的"阻塞"：Flash 擦除

F4 擦一个扇区要 200 ms ~ 1 s，期间 CPU 从 Flash 取指会停。这是全工程唯一需要"任务"的地方。

**解法不是上 RTOS，而是限制时机**：`nvm_save()` 只允许在 `IDLE` 状态调用——此时电机已停、无控制环运行，阻塞 1 秒完全无害。参数保存本来就该在安全状态做。

> 若将来必须在运行中写 Flash，再把擦写函数放到 RAM 执行（`__attribute__((section(".RamFunc")))`），而不是引入 RTOS。

#### 什么时候该改用 RTOS

出现下面任意一条，就说明该重新评估：

- 要接 **TCP/IP**（网络调参、图传回传）
- 要挂 **文件系统 / SD 卡**（录像、日志）
- 要加**视觉跟踪**（图像处理占 CPU 大块，必须任务隔离）
- 多路串口跑**多个协议**并发
- 团队多人协作，模块边界需要硬隔离

**现在这个产品（增稳 + 串口控制）一条都不满足。**

#### 但要按"能迁移"的方式写

虽然不用 RTOS，代码要写得将来能搬过去。三条规则：

1. 每个模块只有 `xxx_step()`，**内部不阻塞**，不写 `while` 等标志
2. 时间判断一律用 `timebase_ms()`，**不用 `delay()`**
3. 模块之间不直接调用对方的 `step()`，由上层按顺序驱动

这样将来真要上 FreeRTOS，只需把 `app_step()` 拆成几个任务，`algorithm/` 和 `control/` **一行都不用改**——因为它们本来就是纯计算、无状态依赖。

```
│   │   ├── math_utils.c/.h     sin/cos 查表、atan2、限幅
│   │   └── ring_buffer.c/.h    环形缓冲
│   └── tests/                  PC 端单元测试（algorithm / control）
└── stm32/                      STM32 HAL / CMSIS（原样引入，禁止修改）
```

**为什么官方 HAL 不放 `src/` 里**

STM32 HAL 和 CMSIS 是**别人写的、永远不改的代码**，放进 `src/` 有两个问题：

1. `src/driver/`（我们的驱动层）和 `src/drivers/`（官方 HAL）只差一个字母，`ls` 和 tab 补全都会看错；
2. 一旦有人为了调 bug 改了 HAL 源码，下次重新生成 CubeMX 就全被覆盖，而且没人知道改过。

所以官方代码整体隔离到根目录 `stm32/`（与 `src/` 平级），`src/` 里每一行都是自己写的、可以随便改的。

唯一例外是 `hal_conf.h`——它本来就是给用户裁剪模块用的，属于**配置**而非源码，所以放 `src/common/`。

## 6. 命名规则

### 6.1 基本规则

| 对象 | 规则 | 示例 |
|---|---|---|
| 目录 | 小写全拼，表示层 | `app/` `control/` `algorithm/` `driver/` |
| 文件名 | 小写下划线，**不带层前缀**（层已由目录表达） | `fsm.c` `hall.c` `svpwm.c` |
| 函数 | `文件名_动作` | `fsm_get()` `hall_decode()` `pid_step()` |
| 类型 | `文件名_t` | `hall_t` `pid_t` `axis_cfg_t` |
| 枚举值 | `文件名大写_值` | `FSM_INIT` `MODE_LOCK` `AXIS_YAW` |
| 宏 / 常量 | 全大写 + 下划线 | `M1_PWM_A_PIN` `PWM_FREQ_HZ` |
| 静态变量 | `s_` 前缀 | `s_adc_buf` `s_hall[MOTOR_NUM]` |
| 全局变量 | **禁止**（用 `xxx_get()` 接口） | — |
| 头文件保护 | 统一 `#pragma once` | — |

> 枚举值在 C 里属于全局命名空间，不跟随类型作用域。`INIT`、`RUN`、`OK` 这类通用值迟早撞车，必须带模块前缀。

**头文件引用**一律从 `src/` 起算：

```c
#include "algorithm/hall.h"
#include "driver/pwm.h"
#include "common/board.h"
```

这样文件移动时只需改一处 include 路径，不会出现 `../../../` 这种脆弱写法。

### 6.2 允许的缩写

只有行业里已经固定的术语才允许缩写，其余一律全拼。

| 允许缩写 | 要求全拼 |
|---|---|
| `pid` `fsm` `svpwm` `imu` `pwm` `adc` `spi` `uart` `gpio` `nvm` | — |
| — | `calibration`（不写 `calib`） |
| — | `feedforward`（不写 `ff`） |
| — | `ring_buffer`（不写 `ringbuf`） |

判断标准很简单：**缩写是否"显然"取决于读者背景**。`svpwm` 同行都认识，`calib`、`ff` 就得猜。宁可长一点，不要让人停下来想。

### 6.3 已定名的取舍

| 候选 | 定名 | 理由 |
|---|---|---|
| `state` / `fsm` / `state_machine` | **`fsm`** | 标准缩写，与 `pid` 同类；`state` 太泛，`state_machine` 函数名太长 |
| `time` / `timebase` / `systime` | **`timebase`** | **避开 `<time.h>`**，见下；语义也比 `systime` 准确 |
| `mode` / `workmode` / `opmode` | **`mode`** | 工程内只有"工作模式"这一个 mode 概念 |
| `protect` / `protection` | **`protect`** | 短，且不会与其它概念混淆 |
| `calib` / `calibration` | **`calibration`** | 与 `feedforward` 保持全拼一致，不能一半缩一半不缩 |
| `utils` / `math_utils` | **`math_utils`** | `utils` 是垃圾桶命名，必须限定领域 |

**`time.c` 为什么必须避开**：GCC 的 `#include <...>` 也会搜索 `-I` 指定的目录。只要 `-Isrc/driver` 在编译选项里，任何一处 `#include <time.h>`（newlib、HAL、第三方库都会用）都可能被解析到工程自己的 `driver/time.h` 上，报出莫名其妙的类型冲突，而且这种错误极难定位。

**文件名要满足"唯一可辨识"**：去掉层前缀后，文件名必须脱离目录也能看懂。所以文件名应该是"这个模块唯一拥有的名词"，而不是一个大类词——`pwm.c` `hall.c` `gimbal.c` 都可以，`state.c` 不行（电机状态、IMU 状态、系统状态都叫 state）。

> 完整的命名决策过程（含 `ctrl/algo/bsp` 为什么改成 `control/algorithm/driver`）见**附录 A**。

#### 7.2.1 霍尔解算（已确认 120° 摆放）

**第一步：确认霍尔读的是哪个磁场。** 这比公式本身更重要，两种情况的架构完全不同。

| | 情况 A：独立 2 极角度磁环 | 情况 B：转子多极磁钢 |
|---|---|---|
| 一圈机械角内的电周期数 | 1 | p |
| 解算得到 | 机械角（直接可用） | 电角度 |
| 机械角 | `θ_mech = θ_解算` | `θ_mech = θ_解算 / p`，**有 p 个解** |
| 上电绝对角 | ✅ 唯一 | ❌ 不知道在哪一个解上 |
| §3 第 2 条"上电即知位置" | 成立 | **不成立**，要改成"IMU 粗定位 + 霍尔精修正" |
| 极对数的用途 | 只用于 SVPWM：`θ_电驱 = p × θ_mech` | 用于解算本身 |

云台直驱电机正常做法是**情况 A**（磁编码器就是 2 极磁环），所以大概率是 A。但"大概率"不能写代码，必须实测。

**第二步：解算公式（120° 版）。**

两路霍尔机械夹角 120°，输出为

```
a = sin θ
b = sin(θ − 120°) = −0.5·sin θ − 0.866·cos θ
```

由 `a + 2b = −1.732·cos θ` 得

```
sin θ = a
cos θ = −(a + 2b) / 1.732 = −(b + 0.5a) / 0.866
θ     = atan2(sin θ, cos θ)
```

代码形式（`2/√3 = 1.1547005`）：

```c
float sin_th = va;
float cos_th = -hall_dir[axis] * (vb + 0.5f * va) * 1.1547005f;
float theta  = atan2f(sin_th, cos_th);
```

> 90° 安装的公式是 `θ = atan2(va, vb)`，两者不能混用。已确认 120°，所以 `hall.c` 里**只保留 120° 一套**，不再做编译期切换——少一个宏，少一处配错。

**第三步：两路各自归一化。** 两颗霍尔的灵敏度、磁隙、偏置都不一样，不归一化会在角度上留下 2θ 周期的误差，典型 1~5°，直接吃掉 M2 的 <1° 指标。

```c
va = (raw_a - offset[axis][0]) / gain[axis][0];   // offset=(max+min)/2, gain=(max-min)/2
vb = (raw_b - offset[axis][1]) / gain[axis][1];
```

偏置和增益靠 `calibration.c` 转一整圈采 min/max 得到（§7.2 已有）。**注意：必须转满一整圈机械角**——情况 A 下就是 1 个电周期，情况 B 下要转满 p 个电周期才算完整，转少了 min/max 采不全，标定结果偏。

**第四步：符号。** `hall_dir[axis]` 取 ±1，处理"b 超前还是滞后 120°"。不靠推算，靠标定：给正转，看解算角度是否单调递增，反了就翻符号。这个参数必须进参数区（§12），不能硬编码。

**第五步：验证极对数（5 分钟，不用写代码）。**

手动匀速转电机轴**一整圈（机械 360°）**，用示波器或万用表看一路霍尔的输出波形，数正弦周期数：

| 数到几个周期 | 结论 | 后续动作 |
|---|---|---|
| **1 个** | 情况 A，2 极角度磁环 | 一切按本文档走，`pole_pairs` 只给 SVPWM 用 |
| **p 个（p>1）** | 情况 B，读的是转子磁钢 | `pole_pairs = p`，再量两路相位差确认可用性（见下） |

数周期这一下顺便把 §2 第 3 项的极对数也定了——**这是全项目性价比最高的一次测量**。

**为什么 p 不能是 3 的倍数（前提：机械 120°）：** 两路霍尔**机械**夹角 120°，相位差 = 120° × p（电角度）。若 p = 3k，则 120°×3k = 360°×k ≡ 0°，两路输出完全同相，`atan2` 拿不到任何相位信息。此时只有一路信号，只能判断角度落在哪个象限的边界，精度退化到几十度，M2 的 <1° 无从谈起。

但这里还有第三种可能：如果设计者是按**电角度** 120° 布的霍尔（即机械夹角 120°/p），相位差恒为 120°，与 p 无关，任何极对数都成立。这种情况实测会看到：

| 实测现象 | 说明 | 是否可用 |
|---|---|---|
| 相位差 120°，且 p % 3 ≠ 0 | 机械 120° 摆放，恰好可用 | ✅ |
| 相位差 120°，且 p % 3 = 0 | **按电角度 120° 摆放** | ✅ 公式照样成立 |
| 相位差 ≈ 0° | 机械 120° 摆放但 p % 3 = 0 | ❌ 失效 |

所以判据不是"p 是不是 3 的倍数"，而是**"两路相位差是不是 120°"**。测相位差比算 p 更直接：双通道示波器同时看两路霍尔，量一个上升沿到另一个上升沿的时间差，除以周期 × 360°。**这一条必须在 M2 之前确认，不能等写完代码再发现。**

**若真的是情况 B 且 p>1**，云台单圈绝对角做不到，架构要改：

```
粗角度 = IMU 陀螺积分（短时准，长时间漂）
精角度 = 霍尔电角度（绝对但不唯一，周期 360/p）
融合   = 用霍尔把陀螺积分"扣"到最近的合法解上
```

这不是小改动——`control/gimbal.c` 要多一条融合路径，M2 从 1.8 周变 3 周，M4 也要受影响。所以先测，再决定。

### 7.3 控制层 `control/` —— 决定"给多少电压"

| 文件 | 职责 | 要点 | 对外接口 |
|---|---|---|---|
| `pid.c/.h` | 通用位置式 / 增量式 PID，带积分限幅、输出限幅、抗饱和 | — | `pid_init(pid_t*, kp, ki, kd, out_max)`<br>`pid_step(pid_t*, err, dt)`<br>`pid_reset(pid_t*)` |
| ⭐ `axis.c/.h` | 单轴串级：位置环 → 速度环 → 电压指令 | **速度环反馈来自霍尔差分，不是 IMU**；IMU 只用于负载侧姿态；电压指令输出 −1~+1（归一化），由 `svpwm` 转成占空比 | `axis_init(axis, cfg)`<br>`axis_set_target(axis, angle, rate)`<br>`axis_step(axis, dt)`<br>`axis_get_vcmd(axis)` |
| ⭐ `feedforward.c/.h` | 反电动势前馈、母线电压前馈、重力补偿、摩擦补偿 | **没有电流环时最重要的模块**，直接决定动态性能 | `feedforward_update(axis, rate, angle)` |
| `gimbal.c/.h` | 三轴协调、轴映射（M1/M2/M3 ↔ yaw/pitch/roll）、限位、回中 | 轴映射做成配置表，机械定型后**只改表不改代码** | `gimbal_init()`<br>`gimbal_set_mode(mode)`<br>`gimbal_step()`<br>`gimbal_get_status()` |

#### 单轴控制结构

```
目标角度 ──►[位置P]──► 目标速度 ──►[速度PI]──► 电压指令 ──►[+前馈]──► SVPWM
              ▲                        ▲                                 │
              │                        │                                 ▼
          霍尔机械角              霍尔差分速度                       三相占空比
```

#### 前馈三项

| 项 | 公式 | 说明 |
|---|---|---|
| 反电动势 | `u_ff = Ke · ω_e` | Ke 从电机参数或标定得到 |
| 母线电压 | `duty = u_cmd / VBUS_NOMINAL` | **用常量 7.2 V**，不是实测值（PC0 超量程，见附录 B B3）。抵消不了母线波动，但至少保证占空比标定一致 |
| 重力 | `u_ff = (m·g·L·cos θ) / Kt` | **仅 pitch 轴需要**（相机重心偏镜头侧） |

> 母线电压前馈本可以吸收电池内阻导致的母线跌落，现在这层补偿没了。**补偿办法**：把 `VBUS_NOMINAL` 做成参数，用实测的平均母线电压填进去，比用标称值准。代价是电池电压变化后要重标。

## 8. 运行时序

### 8.1 中断优先级与时间预算

| 中断源 | 频率 | 优先级 | 执行内容 | 预算 |
|---|---|---|---|---|
| ADC 转换完成（DMA） | 8 kHz | 0（最高） | 霍尔解算 → 控制环 → SVPWM → 写 CCR | < 40 µs |
| SPI2 | 1 kHz | 2 | IMU 数据读取 | < 50 µs |
| USART2 / UART5 | 事件 | 3 | 入环形缓冲 | < 10 µs |
| SysTick | 1 kHz | 4 | 时基、喂狗、应用层调度 | < 5 µs |

**CPU 占用估算**：8 kHz × 40 µs = 32%，1 kHz × 50 µs = 5%，合计约 40%，余量充足。

> **预留方案**：若实测 ADC 中断超 40 µs，可启用 TIM6（8 kHz，优先级 1）把控制环拆出来，ADC 中断只做霍尔解算。默认**不启用**，避免维护两套时基。

### 8.2 时基关系

```
PWM 24 kHz ─┬─┬─┬─┬─┬─┬─┬─┬─┬─┬─┬─┬─    占空比保持不变
ADC 8 kHz   ▲     ▲     ▲     ▲        每 3 个 PWM 周期触发一次（TIM1 RCR=2）
控制 8 kHz  ▲     ▲     ▲     ▲
IMU 1 kHz   ▲           ▲              每 8 个控制周期
应用 100 Hz ▲                   ▲      每 80 个控制周期
```

### 8.3 初始化顺序（`main.c`）

```
时钟 → GPIO → 时间基准 → nSLEEP 拉低（电机保持关闭）
  → ADC → PWM（不使能输出）→ SPI/IMU → UART → NVM 读参数
  → 自检（霍尔 / IMU / 母线电压）→ 状态机进入 IDLE
```

**上电安全**：nSLEEP 由 4.99K 下拉保持低电平，这是安全的。必须等占空比配置成 50%（零电压）后再拉高 nSLEEP，否则上电瞬间会有冲击。

## 9. 数据流

```
① 采样    霍尔 ADC(6ch) ──DMA──► raw[6]
② 解算    raw → 偏置/增益归一化 → 120° 重构 → atan2 → 角度 →（情况 A：机械角直接可用 / 情况 B：÷极对数 得机械角）
③ 控制    目标角 − 实测角 → 位置P → 目标速度 → 速度PI → 电压指令
④ 前馈    + Ke·ω + 重力补偿 + 母线电压归一化
⑤ 调制    α-β 电压 → SVPWM → duty[3]
⑥ 输出    duty[3] → CCR 寄存器 → 半桥
```

每一级都是纯数值接口，便于单独打点观测——这也是 §4.2 规则 3 的实际用途：调试时可以只把 ② 或 ③ 抽出来在 PC 上复算。

## 10. 状态机

```
        ┌──────────┐
        │  INIT    │  时钟 / 外设 / 参数加载
        └────┬─────┘
             ▼
        ┌──────────┐   失败   ┌──────────┐
        │ SELFTEST │─────────►│  FAULT   │
        └────┬─────┘          └────┬─────┘
             ▼                     │ 故障清除
        ┌──────────┐               │
        │   IDLE   │◄──────────────┘
        └────┬─────┘
             │ 收到运行指令
             ▼
        ┌──────────┐  保护触发
        │   RUN    │──────────► FAULT
        └────┬─────┘
             │ 收到停止指令
             ▼
          IDLE

        CALIB 可随时从 IDLE 进入，完成后回 IDLE
```

**关键**：因为霍尔是绝对角度，`IDLE → RUN` **不需要任何对齐动作**，直接闭环。这是本方案相对无感 FOC 的最大简化——省掉了预定位、开环强拖、观测器收敛三个阶段。

## 11. 保护策略

没有电流采样，保护只能靠间接判据：

| 故障 | 判据 | 动作 | 可行性 |
|---|---|---|---|
| 堵转 | 电压指令连续 > 0.9 且角度误差 > 5° 持续 200 ms | 降额 → 停机 | ✅ |
| 霍尔异常 | 原始值超出 [200, 3900] 或连续 N 周期无变化 | 停机 | ✅ |
| 母线欠压 | Vbus < 6.0 V（须 `adc_get_vbus()` 的 valid 为真） | 降额 | ✅ 6.6 V 以下才有效 |
| 母线过压 | Vbus > 9.0 V | 停机 | ❌ **无法检测**，读数早已饱和 |
| IMU 通信失败 | WHO_AM_I 校验失败 / 连续超时 | 降级为单轴锁定 | ✅ |
| 过温 | MCU 内部温度 > 85 °C | 降额 | ✅ 只能看趋势 |
| 看门狗 | IWDG 超时 | 复位 | ✅ |

> **`nFAULT` 引脚悬空，芯片过流/过温后只会自己重启 4 ms，MCU 完全不知道。** 上表是唯一的软件防线，判据阈值不要随意放宽。
>
> **母线过压这一行留着但永远不成立** —— 分压比 1:2 在 7.2 V 就已经饱和，9 V 根本读不出来（附录 B B3）。保留是为了说明"这个保护我们想过，但硬件做不到"，而不是漏了。

### 13.2 风险排序

**第一风险：M4 闭环（基准 2.2 / 悲观 4.5）。** 硬件冻结让这一步的上限变差了——原来霍尔噪声压不住还可以说"改板加 RC"，现在只能靠软件滤波，而软件滤波必然引入相位滞后，直接吃掉相位裕度。这是"稳"和"快"的死结。

如果 M4 卡住，按顺序试三条退路：

1. **降带宽** —— 位置环 `pos_kp` 减半，先让它稳，牺牲抗扰能力
2. **改结构** —— 去掉速度环，位置误差直接乘系数出电压指令（少一个环就少一处振荡）
3. **换反馈** —— 速度改用 IMU 陀螺（噪声比霍尔差分低一个量级），代价是丢掉电机侧信息

**第二风险：M8 整机（基准 3.5 / 悲观 6.0）。** 减振球刚度、相机重心、穿轴摩擦，任何一项变动都要重调。这部分没法靠加班压缩。

**M2 不是风险，是关卡。** 它只花 1.8 周，但如果角度解算错了（装角或极对数搞错），后面全白做。所以 M2 的验收标准"0→360° 连续无跳变"必须严格卡住，不达标不许进 M3。

M2 还有一个隐藏分支：如果测出来是情况 B（霍尔读转子磁钢）且极对数是 3 的倍数，解算直接失效，M2 从 1.8 周变成"要先想别的办法"。这就是 §7.2.1 那个 5 分钟测量必须在开工前做完的原因——**它能把一个 3 周后的灾难提前到第 1 天发现**。

## 14. 编码约定

1. 浮点一律单精度 `float`，开启 FPU（`-mfpu=fpv4-sp-d16 -mfloat-abi=hard`）。

### A.1 层目录为什么用全拼

层名是**架构概念**，会被反复写在文档、代码 review、issue 里，而且没有编译器帮你检查拼错。这类词一旦缩写，读者每次都要在脑子里翻译一遍。

| 旧名 | 新名 | 为什么必须改 |
|---|---|---|
| `ctrl/` | `control/` | `ctrl` 是键盘按键的固有含义；且只省 3 个字母 |
| `algo/` | `algorithm/` | `algo` 在交易/刷题语境里是"算法交易""算法题"；且工程里只有"控制算法"这一个 algorithm |
| `bsp/` | `driver/` | **最该改的一个**。BSP（Board Support Package）在不同团队含义完全不同：有人指官方 HAL，有人指板级初始化，有人指外设驱动。含义不唯一的术语不能进目录名 |
| `drivers/`（HAL） | `stm32/`（根目录） | 与新的 `driver/` 只差一个 `s`，靠肉眼区分不可靠；且官方代码不属于本工程，应与 `src/` 平级隔离 |

**为什么 `fsm` 能留、`bsp` 不能留**：

- **构件类型名** → 可以缩写。`fsm` `pid` `svpwm` 是行业内唯一解（Zephyr 的状态机框架就叫 SMF），任何上下文里都不会被误解。
- **层名** → 必须全拼。层名是**本工程的架构划分**，没有行业标准。

一句话：**缩写只给构件类型，层名一律全拼。**

| `common/` | 已是全拼，含义明确 |
| `tests/` | 已是全拼 |

#### B3 专项：母线电压怎么用

分压比 1:2，所以 ADC 读数对应 `Vbus = ADC × 3.3 / 4095 × 2`，但在 6.6 V 以上饱和。这决定了三件事：

| 用途 | 可行性 | 做法 |
|---|---|---|
| 母线电压**前馈** | ❌ 不可行 | `svpwm_calc()` 的 `vbus` 传参数 `vbus_nominal`（默认 7.2 V） |
| 母线**过压**保护（>9 V） | ❌ 不可检测 | 只能依赖输入端 TVS（B6） |
| 母线**欠压**检测（<6.6 V） | ✅ **可行** | 6.6 V 以下退出饱和，读数有效。6.0 V → 3.0 V → ADC ≈ 3723，可判别并降额 |

**实现要点**：PC0 保留在 ADC 扫描序列里（下标 6），`adc_get_vbus()` 返回两个东西——原始 ADC 值 + 一个 `valid` 标志（`raw < 4000` 时有效）。`protect.c` 只在 `valid` 为真时判断欠压，避免把饱和值误判成正常。

**电流注入**：3.6 V 经引脚钳位二极管灌入 VDDA，电流约 72 µA（(3.6−3.3)/24.95K）。规格内（钳位限值 ±5 mA），不会损坏芯片，但会在 VDDA 上叠加一点噪声——`adc.c` 里霍尔通道的采样窗口建议避开与母线通道相邻的时刻。

### B.11 装配注意（不是设计问题，但接错会炸）

**40P FPC 与 BOD12-11 的 J1 引脚顺序相反**：

- 40P 侧：`+3.3V / GND / 霍尔 / 相 ×6`
- BOD12-11 侧：`相 ×6 / 霍尔 / GND / VIN`

**线束必须交叉。** 直连会把 3.3 V 直接落到相线上，上电即短路。建议在线束上做防呆（不同颜色或键位），这比在固件里加任何保护都有效。

### B.12 待确认的复用

PA6 同时接了 `R15 100R → J3-5(PWM1)` 和 `R4 4.7K → Q1 基极`，Q1 集电极经 R3 10K 上拉由 PC11 读取。需确认是有意设计（PWM 输入 + 状态回读共用）还是布板遗留——这直接决定 §2 待定项 5 的答案。

**若确认是输入**：PA6 配为输入捕获，PC11 读回 Q1 状态可用于判断外部信号极性。
**若确认是输出**：Q1 会在输出高电平时导通，把 PC11 拉低，可作为一个"输出自检"信号，但要注意基极电流经 4.7K 会额外加载 PA6。
